jobhunt - system design

An autonomous job-application pipeline that runs on David's Mac. It discovers postings, decides which ones matter, writes a tailored resume, fills and submits the actual application forms, reads the inbox for outcomes, and reports back once a day. Human input is reserved for the ~5% of decisions that genuinely need it.

§The pipeline at a glance

Seven stages. Each is a separate process fired by its own timer, and the only shared state is one SQLite database (out/tracker.db). A stage reads rows in the status it owns, does its work, and writes rows forward to the next status. No queues, no services, no IPC. If any stage dies, nothing else notices or cares; the rows just wait.

The core design bet A boring architecture survives. Every alternative considered (task queues, a web service, cloud workers) adds a failure mode that can't be debugged at 2am with sqlite3 and tail. The entire system is: timers fire python scripts, scripts move rows through statuses, browsers do what a human would do. Anyone (human or agent) can inspect any part with two commands.

§Posting lifecycle (the state machine)

Every posting is one row in postings, and its status column is the whole coordination mechanism. These are the real transitions:

 │                │                                         │
 │                └──sprint.py (fast lane: new posting──────┤   (4-min timer race:
 │                    tailor + submit in one pass)          │    speed-to-apply wins offers)
 │                                                          │
  ├──▶ filtered_out   wrong role / season / duplicate posting ├──▶ manual   needs a human:
 │      (82% of everything discovered - by design)          │      unanswerable required question,
 │                                                          │      CAPTCHA, unsupported ATS,
 ├──▶ skipped        David's explicit rules               │      broken login. Parks aside -
 │      (fall purge, P26 ban, WaaS pause)                   │      never blocks the queue.
 │                                                          │
 └──▶ failed         posting closed, board broken ────────┘      retryable failures loop
        (genuine dead ends after retries)                          back to ready with backoff
Manual is a parking lot, not a roadblock The single most important property: a posting that needs human input steps OUT of the flow. Rows behind it keep moving. The daily digest surfaces manual rows with the exact blocking question, and David's reply ("skip X" / "for Y: june 1st") is parsed and applied automatically.

1Discovery - nine watchers, one funnel

Supply is the ceiling on everything downstream, so discovery is deliberately over-inclusive: cast wide, let the filter be the taste. All watchers write the same row shape with a per-source posting_id convention so re-scrapes dedupe for free.

The community-maintained Summer/Winter 2027 lists. Diff-polled: only rows not already in the DB get inserted. Highest volume, lowest signal-per-row.

A-D startup scout

abc_startups.pyabc_backfill.py

The clever one. Harvests funding announcements (TechCrunch/Crunchbase/VentureBeat RSS) and VC portfolio pages (a16z…), LLM-extracts {company, round}, keeps Series A-D, then resolves each company's real careers page (official domain → careers links → ATS board; slug guessing only as a last resort) and polls the public Greenhouse/Lever/Ashby/Workable/SmartRecruiters JSON APIs forever. A TechCrunch-archive backfill seeded ~3 years of past rounds. Finds roles that never hit any list.

Big-co direct boards

17 verified public JSON boards for companies that post directly and skip the lists: Stripe, OpenAI, Databricks, quant firms. Cheap JSON polling, no scraping.

2Filter - David's taste, enforced in code

watcher/filter.py + profile/profile.yaml. Runs on every new row. ~82% of discovered postings die here, which is the system working: the lists are full of mechanical-engineering co-ops and fall-term roles.

rulewhat it enforces
roles_includeeverything engineer-adjacent (word-boundary matched): SWE / ML / AI / infra / MTS / founding, product, forward-deployed, solutions engineer / SRE / security / embedded software / mobile / data science / quant / PM & APM

3Tailor - one resume per job description

drip.py (hourly) pulls queued rows, fetches the JD, and has Claude reword the LaTeX resume against it. Capped at 100/day.

Reword-only law

Claude may reorder and rephrase bullets from the approved resume/bullet_bank.md (every number pre-verified). It may never invent a project, employer, metric, or credential. Grad date is track-based (track.py): intern apps May 2028, full-time apps May 2027 (the real early-graduation plan, confirmed).

Quality gate

Each PDF gets structural validation + quality metadata written beside it. A resume that fails the gate parks the posting as manual rather than sending something broken. (A missing-metadata bug once stranded 13 postings - now reconciled automatically.)

Sprint lane

sprint.py (every 4 min) races brand-new postings through tailor + submit in one pass. Speed-to-apply matters: early applications get read by humans; day-3 applications get read by rejection filters.

4Submit - the part that touches the world

submit_daemon.py is a resident local dispatcher. It wakes every 30 seconds, groups ready rows by the shared ATS lane classifier, and drives real application forms with headless Playwright. This stage has the most armor because failures here can be irreversible (double-submits) or invisible (silent no-ops).

Per-ATS adapters apply/*.py

Greenhouse · Lever · Ashby · Workday · Workable · SmartRecruiters · Rippling · email. Each knows one vendor's DOM: where fields live, how uploads work, what a confirmed submission looks like. Detection routes by URL (with redirect-chasing for postings that link a homepage).

ATS lanes

Greenhouse, Lever, Workable, and Rippling share the direct lane with bounded concurrency. Workday has a single-worker lane. Ashby remains behind a breaker, and unsupported ATSs are parked as manual instead of blocking other rows.

directworkdayashby breaker

Process isolation

Every posting runs in its own killable subprocess (submit_worker.py) with a hard 300s deadline. A hung browser cannot take down the resident dispatcher.

5-min posting capper-lane budgets

Submission ledgers

applications table has a UNIQUE key per posting; canonical posting dedupe prevents mirrored rows from creating duplicate applications before any external form is touched. submission_attempts is the append-only attempt ledger for ATS, lane, worker, timestamps, outcome, confirmation, and artifacts. "Submit clicked but unconfirmed" quarantines the row instead of retrying.

never double-applyattempt telemetry

Workday account self-recovery

Workday requires per-tenant accounts (30 on file, generated passwords stored in the DB). On sign-in failure the system clicks Forgot Password, catches the reset email in Gmail, sets a new password, stores it, and retries - once per tenant per day.

self-healing

Ashby canary policy

Ashby is disabled by default and its only policy source is SQLite state in out/tracker.db. Operators inspect it with manage_lanes.py status ashby and preview ashby, then use enable-canary ashby or pause ashby only at reviewed gates. The evidence tiers are 180, 90, and 45 minutes. 3 and 10 confirmed submissions advance the lane. A 24-hour spam breaker rolls back one tier. Uncertainty pauses. Click-uncertain postings are never retried. Postings with completed attempts are never reused.

disabled by default

Ashby browser gate

The persistent profile lives under ignored .jobhunt-browser-profiles/ashby. When ordinary Chrome is in use, Ashby requires a separately installed Chrome for Testing. Stable Chrome is rejected for native smoke and ordinary Chrome must never be hidden. Verification uses scripts/verify_ashby_browser.py --check-only without launch or System Events, and reviewed --about-blank only after a dedicated target exists. It reports only executable, process name, profile path, user agent, navigator.webdriver, plugin count, and visibility for the dedicated process. No browser fingerprint fields are used.

no stable Chrome smoke

Ashby rollout gate

Live rollout remains deferred. The exact order is: install dedicated browser, about:blank verification, integrate the branch, back up live DB and run PRAGMA integrity_check, inspect read-only preview, get explicit approval for one irreversible submission, run one cycle, immediately pause, then inspect telemetry. Service reload is pending until those gates pass.

manual approval required

Deferred courtesies removed

A "don't submit while David is gaming" check matched the idle Steam client and silently froze the pipeline for six days. Deleted: headless submissions never show a window anyway. Lesson enshrined below.

5Form Q&A - the judgment layer

apply/qa.py (58 functions, the most nuanced file in the repo). Application forms ask questions; this decides what may be answered and how.

form controls ──▶ deterministic answers (name, email, school, work auth… from profile.yaml)
                       │
                       ├──▶ HARD-BLOCKED topics - never auto-answered, even if required:
                       │      demographics · salary numbers · references · prior-employment
                       │      claims · household questions · anything a wrong answer misrepresents
                       │      └─ required + blocked → posting parks as manual
                       │
                       ├──▶ SOFT topics - truthful best-judgment only when the field is
                       │      required (clearance: none · grad timing · availability);
                       │      optional versions stay blank (silence is free)
                       │
                       └──▶ essays - full-auto from the STORY BANK only
                              (docs/interview_stories.md): real stories, real numbers,
                              80-150 words, no em dashes, never references this pipeline
The self-reference incident The story bank once contained a bullet describing this very pipeline. A recruiter read an essay generated from it and concluded (correctly) that a bot filed the application: "I can't tell what you wrote from what a model assembled." The bullet is gone, replaced by an agent-factory story about the same engineering without the tell. Rule: the system may never describe itself in an application.

6Tracking - the inbox is the source of truth

inbox.py (every 30 min) reads Gmail, classifies every job-related email with Claude (OA invite / interview / recruiter reply / rejection / offer), labels and archives, extracts deadlines, and writes inbox_events keyed by company.

Outcomes join back onto applications by normalized company name - which is why the sheet can show "🟠 OA received" without anyone updating anything.

7Reporting - one digest, one sheet, zero spam

Daily digest (6pm ET, email + Telegram)

Casual tone, skimmable in 30 seconds: what needs David (deadline-sorted), stuck applications with the exact blocking question, unverified submissions, pipeline stats, top failing ATSs, per-ATS confirmed ratios, lane queue depths, and Ashby breaker state when paused. Replies are commands: "skip X", "for Acme: I can start June 1" - parsed and applied. All other notification email is muted to a log file.

Live Google Sheet

Three tabs, rewritten every 30 min (one-way; edits never read back): a chill dashboard (sent this week, heard-back %, outcomes), Applications with color-coded status badges derived from inbox_events, and the live pipeline. The glanceable answer to "how's it going".

§Safety properties (the invariants)

Never misrepresent

Hard-blocked topics stay human. Essays only from verified stories. Unanswerable required field = that application stops. A fabricated answer is a bug of the worst class.

Never double-apply

Ledger UNIQUE constraint + company-level freeze + "unconfirmed submission" quarantine. A maybe-submitted application is never retried.

Bounded blast radius

Per-posting subprocess kill · run budgets · caps (8/run, 100 tailors/day) · one-recovery-per-tenant-per-day. No component can spend more than its budget of time or actions.

Everything auditable

Every status change carries a reason in last_error. Every auto-answer logs to qa_answers.log. Every filled form is screenshotted (14-day rotation). "Why did X happen" is always answerable.

§Design lessons (earned the hard way)

Observability beats cleverness

The two worst incidents (six-day Steam freeze, missing chromium binary) weren't design flaws - they were silent failures in a system that had no immune response. The fix wasn't a redesign; it was health checks that observe outcomes (fresh DB writes, log recency), never process existence.

Failures must not consume the success budget… but need their own budget

The submit loop counts successes toward its 8-target, so failures don't starve throughput. But unbudgeted failures once stretched a run to 77 minutes (each slow-failing Workday row legitimately burning its 5-min cap, back to back). Both bounds are needed: per-item caps AND a whole-run budget.

Visibility ≠ existence (browser automation)

LinkedIn/ATS DOMs contain hidden duplicate buttons. count() > 0 found them; click() then waited 45s for visibility and timed out - burning invite budgets on doomed attempts. Every affordance check is now isVisible().

Park, don't block

Any item needing a human steps out of the flow into manual with the exact question attached, and the digest turns those into one skimmable list with reply-commands. The pipeline's job is to make the human the exception path, not the approval path.

The system may never describe itself

An application essay that mentions the application pipeline converts "impressive candidate" into "bot detected". Self-reference is scrubbed from every model-visible artifact.
